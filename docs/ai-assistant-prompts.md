# ИИ-консультант — промпты и что он должен уметь отвечать

Этот документ — прикладное продолжение [карты продукта](product-map.md): §2 (тариф), §4 (S27 «ИИ-консультант», S28 «Ежемесячный разбор»), §5 (F081–F088), §11 («Роль ИИ и стоимость Pro»). Он ничего не решает заново — только переводит уже принятые решения в конкретные промпты, примеры вопросов и привязку к реальным полям кода, чтобы с ним можно было сразу реализовывать.

Главное правило унаследовано из §11 карты продукта и повторяется здесь без изменений, потому что на нём держится весь документ:

> Все числовые утверждения в финансовом ответе привязываются к результатам расчётного модуля. Если данных мало или они устарели, ИИ сообщает об этом.

Практически это значит: модель никогда не считает деньги сама. Она получает уже посчитанный код (те же формулы `famcoin_core`, что рисуют экраны) и облекает их в связный ответ на языке интерфейса. Один вопрос — один снимок готовых чисел, ноль свободной арифметики в промпте.

## 1. Контекст, который получает модель

Перед каждым ответом собирается JSON-снимок — те же данные, что уже показывают экраны «Обзор», «Расходы», «Бюджет», «Капитал», «Долговая нагрузка». Ничего не вычисляется заново специально для ИИ: снимок — это просто сериализация уже существующих геттеров `AppState`.

Обязательные поля снимка (источник — `app/lib/state/app_state.dart`, если не указано иное):

```jsonc
{
  "period": { "month": "2026-09", "todayDay": 29, "daysInMonth": 30 },
  "report": {                 // AppState.reportFor(month) → PeriodReport
    "income": 74000000, "expense": 68100000,
    "result": 5900000,        // report.result — доходы минус расходы
    "cashFlow": 300000        // report.cashFlow — фактическое движение денег
  },
  "dailyLimit": {              // AppState.dailyLimit / dailyLimitAvailable / dailyLimitCarry
    "amount": 500000, "availableToday": 320000, "carry": -180000
  },
  "budget": {                  // AppState.budgetUsedPercent / monthElapsedPercent / limits + limitStatusFor
    "usedPercent": 62.0, "elapsedPercent": 71.0,
    "limits": [{ "category": "food", "limit": 10000000, "spent": 6500000 }]
  },
  "expenseTypeSplit": { "mandatory": 30000000, "regular": 25000000, "discretionary": 13100000 }, // AppState.expenseTypeSplit
  "categories": [{ "id": "food", "amount": 6500000, "momPercent": -12 }],  // AppState.categoriesFor(month) и categoriesFor(prevMonth) + процент разницы — та же арифметика, что уже есть в expenses_tab.dart::delta() (сейчас это локальная функция экрана, для снимка её нужно вынести на уровень AppState)
  "forecast": {                // AppState.monthEndForecast → MonthForecast
    "estimate": 8944000, "rangeLow": 7200000, "rangeHigh": 10700000,
    "remainingObligations": 3000000, "expectedRegularSpend": 4500000
  },
  "capital": { "money": 8944000, "liabilities": 2286818, "capital": 6657182 }, // ledger.netWorth()
  "debtLoad": {                 // AppState.debtLoadStatus → DebtLoadStatus
    "totalDebt": 2286818, "monthlyPayments": 150000,
    "incomeSharePercent": 20.3, "paidPercent": 41.0
  },
  "observations": {             // те же пороги, что уже отфильтрованы для экрана — см. §4.3
    "eveningDiscretionaryShare": 34.0,
    "unplannedLargeExpenses": 2,
    "paydaySpendRatio": 1.8,
    "recurringShareOfIncome": 24.0
  },
  "familyMode": false,
  "locale": "ru"                // или "kk" — ответ строго на языке интерфейса (§12 карты продукта)
}
```

Правила сборки снимка:

- Любое поле, которого код не смог посчитать (например, `budgetUsedPercent == null`, лимитов нет), **не подставляется нулём** — передаётся `null` с явной причиной («лимиты не заданы»). Модель обязана сказать «не знаю» / «эта величина не задана», а не досочинять правдоподобное число.
- В семейном режиме разбивка «для кого» (`AppState.expenseByWho`) добавляется в снимок, только если сам вопрос касается конкретного человека — не передаём лишние личные данные по умолчанию.
- Снимок стоит одного показа пользователю запроса (F088: контроль отправляемого контекста) — экран консультанта должен уметь показать, что именно ушло в модель, тем же принципом, что уже есть у CSV-экспорта (D58).

## 2. Системный промпт (черновик, RU)

```
Ты — финансовый консультант FamCoin. Ты объясняешь ЦИФРЫ, которые уже посчитал код
приложения (раздел JSON «context» в этом запросе), а не считаешь деньги сам.

Правила без исключений:
1. Любое число в ответе должно быть взято из context или прямо из него выведено
   (например, разница двух чисел context). Если нужного числа в context нет —
   скажи прямо: «этого у меня нет» — и предложи, какой экран открыть, а не гадай.
2. Ты никогда не создаёшь, не удаляешь и не изменяешь операции сам. Если пользователь
   просит записать расход — объясни, что для этого есть форма или голосовой ввод,
   не делай вид, что уже записал.
3. Если ты предлагаешь изменение (новый лимит, метод бюджета, план погашения долга) —
   это ТОЛЬКО предложение с расчётом «было / станет». Явно скажи, что оно не применится,
   пока пользователь не подтвердит кнопкой. Ничего не меняется от одного текста ответа.
4. Ты не даёшь индивидуальных инвестиционных или юридических советов. Общие объяснения
   («что такое ставка», «как считается КДН») — можно; «куда вложить деньги» — нет.
5. Наблюдения о поведении — это закономерность, не оценка. Без «слишком много»,
   «нужно меньше тратить», нотаций и стыда. Формулировка нейтральная — как в самом
   приложении: «X% свободных трат — после 20:00», а не «вы тратите слишком много вечером».
6. Отвечай на языке context.locale (ru или kk), не переключайся сам.
7. Если данных за нужный период мало (например, меньше месяца истории) — так и скажи,
   не выдавай приблизительную оценку за точную.
8. Ты видишь данные только этого владельца журнала. Если context не содержит разбивку
   по конкретному члену семьи — не предполагай и не проси личные данные о нём.
```

Промпт рассчитан на модель с вызовом инструментов (tool use) — провайдер ещё не выбран (карта продукта §11, §19), Claude — кандидат, не утверждённая зависимость. Ниже — не API-специфичный набор возможностей, а список того, что должно быть доступно как инструмент, а не как встроенное знание модели.

## 3. Возможности (F081–F088) → примеры вопросов и привязка к коду

### 3.1 F081/F082 — чат и объяснение показателя

Прямые вопросы о готовых числах из снимка — самый частый случай, ответ без пересчёта.

| Вопрос | Источник в context |
|---|---|
| «Сколько я потратил на еду в сентябре?» | `categories` → `food.amount` |
| «Хватит ли мне денег до конца месяца?» | `forecast.estimate` / `rangeLow`–`rangeHigh` |
| «Почему дневной лимит сегодня всего 3 200 ₸?» | `dailyLimit.carry` — перенос с прошлых дней (D64); объяснить именно перенос, а не будто лимит стал меньше сам по себе |
| «Почему в прогнозе диапазон, а не одно число?» | `forecast` целиком — объяснить, что это сценарий ±25% от ещё не потраченной части обычных трат (`forecast.dart`), а не статистическая вероятность (формулировка уже честная после D67) |
| «Как дела с бюджетом?» | `budget.usedPercent` против `budget.elapsedPercent` — «потрачено X% лимита, прошло Y% месяца» |
| «Что такое движение денег и чем оно отличается от «доходы минус расходы»?» | `report.cashFlow` vs `report.result` — типовой вопрос именно потому, что раньше эти два числа путались в интерфейсе (D67 в `decisions.md`) |
| «Бұл айда азық-түлікке қанша жұмсадым?» (то же самое по-казахски, категория «Азық-түлік» — уже используемое название в приложении) | `categories` → `food.amount`, ответ на `context.locale = "kk"` |

### 3.2 F083 — проверка сценария через расчётный модуль

Единственная категория, где ответ требует не просто прочитать снимок, а **вызвать ту же чистую формулу ядра с изменёнными входами** — как отдельный инструмент, не как арифметику модели.

- «Если я куплю телефон за 250 000 ₸ сегодня, что будет с прогнозом на конец месяца?» → вызвать `forecastMonthEnd(...)` с `current`, уменьшенным на 250 000 ₸, и вернуть новую `estimate`/диапазон рядом со старой.
- «Могу я поднять лимит на кафе до 30 000 ₸ и не выйти за общий бюджет?» → пересчитать `budgetUsedPercent` с изменённым лимитом этой категории.
- «Сколько я скоплю на цель за 6 месяцев при взносе 20 000 ₸?» → `goalStatus`/`goals.dart` с гипотетическим взносом, не с текущим.

Инструмент вызывает ровно тот же Dart-код, что и экран (`packages/famcoin_core/lib/src/formulas/*.dart`), просто с другими параметрами — гарантия, что ответ «если бы» никогда не разойдётся с тем, что покажет экран, если пользователь действительно так сделает.

### 3.3 F085 — объяснение аномалий и подписок

Ровно те 4 сигнала, что уже считает `AppState`/`analytics_common.dart::observations()` для карточки «Наблюдения» на «Обзоре» — **с теми же порогами**, иначе консультант в чате будет противоречить тому, что человек видит на экране:

| Сигнал | Функция | Порог показа |
|---|---|---|
| Вечерние свободные траты | `eveningDiscretionaryShare` | доля ≥ 20%, и не меньше 2 операций с указанным временем (иначе `null` — «не показываем наблюдение, которое ничего не измеряет») |
| Крупные траты без лимита на категорию | `unplannedLargeExpenses` | сумма покупки ≥ 20 000 ₸ и категория без лимита; исключены покупки, привязанные к плановому платежу |
| Траты в дни дохода против обычных | `paydaySpendRatio` | отношение ≥ 1.3 |
| Доля постоянных платежей от дохода | `recurringShareOfIncome` | ≥ 30% |
| Резкое изменение категории месяц-к-месяцу | `observations()`, сравнение с прошлым месяцем | |Δ| ≥ 20% |

Формулировка в промпте (правило 5 выше) обязательна именно здесь: это самое чувствительное место, где легко скатиться в поучения.

### 3.4 F086 — подбор метода бюджета

Пять методов из §9.5 карты продукта («Просто учёт», «Лимиты категорий», «50/30/20», «Конверты», «Сначала себе»). Консультант объясняет ограничения выбранного метода по факту снимка (например, «Конверты» требуют полного распределения дохода — если в context видно, что часть дохода не распределена, сказать об этом честно), а не рекламирует один метод как лучший.

### 3.5 F087 — предложение изменений с подтверждением

Механика уже зафиксирована в §11 и проверяется сценарием T35 («ИИ предложил изменение, пользователь отказался → ни баланс, ни бюджет не изменены»): предложение — отдельная сущность (`AIConversation`/предложенная команда), не выполняется само. Ответ модели в этом случае обязан явно указать «было → станет» и закончиться приглашением нажать «Применить», а не имитацией того, что действие уже сделано.

Пример: «Предлагаю поднять лимит на транспорт с 15 000 ₸ до 20 000 ₸ — последние три месяца вы стабильно тратите 18–19 тысяч. Проверьте и примените изменение ниже».

### 3.6 F084 / S28 — ежемесячный разбор

Отдельный (не чатовый) экран, но те же правила заземления. Разбор строится из тех же полей снимка за закрытый месяц плюс ссылки на исходные отчёты — «Изменения, причины, предложения» (реестр экранов). Не описывается подробно здесь отдельно, так как это форма подачи того же материала из §3.1–3.5, а не новый набор данных.

## 4. Явные границы

Не делает никогда, независимо от формулировки вопроса:

- Не советует, куда инвестировать, не даёт юридических советов — общие объяснения понятий можно, персональные рекомендации нельзя.
- Не создаёт, не редактирует и не удаляет операции сам — только предлагает и ждёт подтверждения через обычную проверяемую команду приложения (§11).
- Не осуждает и не морализирует — наблюдения нейтральны, как уже сформулировано в самом приложении.
- Не обещает того, чего нет в продукте (сверка с §2/§4 — если возможности нет в тарифе пользователя, так и сказать, а не притвориться, что она есть).
- Не путает данные членов семьи без явного запроса именно по ним.
- Не выдаёт диапазон/оценку за точное число там, где формула сама признаёт неопределённость (`forecast`, линейный ориентир §9.4).
- Не имеет прямого доступа к базе, банковским платежам или журналу в обход снимка/инструментов.

## 5. Квоты, отказоустойчивость, язык (F088)

- Ответ строго на языке интерфейса пользователя (RU/ҚАЗ) — локализация распространяется и на ответы ИИ (§12 карты продукта: «Локализация распространяется на... ответы ИИ»).
- Повтор одного и того же вопроса (двойной тап, обрыв сети) не должен списывать квоту дважды — тот же принцип идемпотентности по `commandId`, что уже есть у обычных команд (D53).
- При исчерпании квоты или недоступности провайдера — честное сообщение и рабочий ручной путь остаётся, тем же принципом, что уже действует для голоса и чека (сценарий T30 карты продукта: «Микрофон/камера запрещены или облако недоступно → Сохранён ручной путь ввода»): «Потеря сети, ошибка модели или исчерпание квоты не мешают ручному учёту» (§11).
- Остаток квоты виден пользователю в приложении (§11), не только в логах сервера.

## 6. Открытые вопросы перед реализацией

Не решается этим документом — переносится в `decisions.md`, когда будет принято:

1. Конкретный провайдер модели и регион размещения (§11, §19 карты продукта — ещё не выбран).
2. Точные квоты (сообщений/токенов в год на Pro) — после измерения реальной себестоимости, как и для голоса/чеков (§19).
3. Формулировки примеров на казахском выше — рабочий черновик; как и голосовой корпус (§10.2), требует проверки редактором и на реальных вопросах перед выпуском.
4. Список доступных «инструментов» (F083) — из этого документа очевиден состав (пересчёт прогноза, лимита, цели), точные сигнатуры вызовов остаются на реализацию.
