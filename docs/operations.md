# FamCoin — эксплуатация

Короткое руководство: как понять, что приложение живо, что делать при
тревоге, как проверять нагрузку и восстанавливать данные. Решения и причины —
`docs/decisions.md` (D13, D71, D72).

## Как устроено

```
телефон / браузер ──HTTPS──▶ caddy ──▶ web (nginx) ──/api──▶ api (Dart) ──▶ db (PostgreSQL 18)
```

Четыре контейнера (`docker compose ps`), секреты в `.env` (не в git).

## Как понять, что всё хорошо

| Проверка | Команда | Ожидаемо |
|---|---|---|
| Приложение и база живы | `curl https://coin.edudev.kz/api/health` | `{"ok":true}` |
| Контейнеры | `docker compose ps` | все `running`, api и db `healthy` |
| Свежая копия базы | `ls -lt /opt/famcoin/backups \| head -3` | файл не старше суток |
| Сторож | `tail /opt/famcoin/backups/watchdog.log` | пусто или редкие записи |

**Сторож** (`deploy/watchdog.sh`) запускается из cron раз в минуту и сам
пишет в Telegram (админ-чат из `.env`), пока всё в порядке — молчит.

| Сообщение | Что значит | Что делать |
|---|---|---|
| «/api/health не отвечает 3 мин. подряд, перезапускаю api» | API завис или потерял базу; сторож уже перезапустил api | Ждать сообщения «снова работает». Если не пришло — `docker compose logs --tail 100 api db` |
| «после перезапуска всё ещё не отвечает» | Перезапуск не помог | Зайти на сервер, `docker compose logs`, при необходимости `deploy/restore.sh` |
| «контейнер … не запущен» | Контейнер упал, сторож его поднял | Разобрать причину по `docker compose logs <сервис>` |
| «диск заполнен на …%» | Место кончается | `docker system df`, `du -sh /var/lib/docker /opt/famcoin/backups` |
| «резервной копии базы нет больше 26 часов» | Не сработал cron или дамп | `tail backups/backup.log`, запустить `deploy/backup.sh /opt/famcoin` вручную |
| «резервная копия не проходит проверку» | Копия не восстанавливается или журнал в ней повреждён | Сразу сделать свежую копию, запустить `deploy/verify-backup.sh`, разобрать вывод |
| «проверка целостности журнала нашла проблемы» | В рабочей базе несбалансированная операция или битая ссылка | Не править руками: снять копию и разобрать по `deploy/integrity.sql` |
| «сертификат истекает» | Caddy не смог продлить сертификат | `docker compose logs caddy`, проверить, что открыты 80 и 443 |

Сторож не заменяет внешний мониторинг: если упадёт сам сервер, он ничего не
скажет. Поэтому дополнительно заведите бесплатный **UptimeRobot** (или
аналог) на `https://coin.edudev.kz/api/health` с уведомлением в Telegram.

## Резервные копии

- Ежедневно в 03:00 (`deploy/backup.sh`): дамп, хранение 14 дней, копия
  файла в Telegram-чат админа.
- Раз в неделю сторож разворачивает последнюю копию во временной базе и
  проверяет целостность журнала (`deploy/verify-backup.sh`). Вручную:
  `deploy/verify-backup.sh /opt/famcoin` — рабочую базу не трогает.
- Восстановление: `deploy/restore.sh <файл.sql.gz>` (останавливает API,
  **заменяет** базу, запускает API).

## Что защищает от падения под нагрузкой

| Место | Мера | Зачем |
|---|---|---|
| Вход, регистрация, смена пароля | Не больше 3 одновременных операций bcrypt, очередь до 60, дальше быстрый отказ 503 `busy` | Пачка входов занимала весь пул соединений и замораживала приложение (замер: `/state` 13 с вместо 0,2 с) |
| nginx | 5 запросов/с на адрес для входа и регистрации, 30/с на остальное API; ответ 429 `rate_limited` | Перебор паролей и флуд не доходят до базы |
| База | Для API: запрос не дольше 60 с, ожидание блокировки 15 с, транзакция без движения 30 с | Зависший запрос не держит блокировку пользователя и соединение |
| API | Ответ клиенту не дольше 30 с (504 `timeout`); ошибка в фоне пишется в журнал, а не роняет процесс | Один сбой не превращается в недоступность |
| Кеш журналов | Не более 200 владельцев и 300 000 операций суммарно | Память не растёт от «тяжёлых» пользователей |
| Контейнеры | Логи до 3×10 МБ, api ограничен 1 ГБ памяти | Диск и общий с другим проектом сервер не заполняются |
| Данные | Уборка старых сессий, принятых команд (60 сут.), уведомлений (180 сут.) каждые 6 часов; профиль не больше 32 КБ | Таблицы не растут бесконечно |
| Рассылка | До 500 сводок за минуту, по 8 одновременно; Telegram и push с таймаутами | 1000 сводок в 8:00 уходят за минуты, а не блокируют друг друга |

## Проверка нагрузки

Тесты создают тестовые аккаунты, поэтому запускаются **только на локальном
стенде** (`docker compose up -d db api`), не на боевом сервере.

```bash
python3 deploy/concurrency_check.py            # двойное нажатие, повторы, гонки, некорректные суммы
python3 deploy/loadtest.py --users 1000        # 1000 пользователей: наплыв, активный день, шторм входов
```

Оба запускаются и в CI (`.github/workflows/ci.yml`) при каждом пуше.

## Когда масштабироваться

Один экземпляр API и одна база рассчитаны с большим запасом на тысячи
пользователей (см. замеры в `docs/decisions.md`, D72). Сигналы, что пора
что-то менять:

1. `docker stats`: api постоянно около 100% процессора → вынести рассылку и
   Telegram в отдельный процесс и запустить второй экземпляр API за nginx
   (журналы в памяти проверяются по ревизии, поэтому это безопасно).
2. В журнале db строки `duration: …` дольше 500 мс (включено
   `log_min_duration_statement`) → смотреть запрос и индексы.
3. Ответ `/state` у активных пользователей больше 2–3 МБ → добавить
   выдачу «с ревизии N» вместо полного журнала.
4. Диск или память сервера заполнены на 80% → увеличить сервер.
